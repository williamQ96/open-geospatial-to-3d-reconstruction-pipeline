# Fixed people in scene explorers

This local design describes a reusable named-person class for campus, venue and indoor explorers. A scene may configure a documented real person or a fictional character without placing project-specific identities in the template. Use licensed visual references and verify public roles; distinguish stylized inferences, scripted dialogue and unverified traits from verified biography. Do not imply that a scripted line is an authentic quotation.

A person configuration should provide a stable identity, scene identifier and coordinates in that scene, a source-backed display name and concise card fields, an optional vetted profile link, a base character template plus editable appearance parameters, and behavior. Behavior can be fixed at a point or follow a bounded sequence of waypoints at a declared speed, pausing at either endpoint before reversing. Position, ground sampling, route collision and entrance clearance belong to the scene adapter; indoor and outdoor scenes must not share coordinates without an explicit transform. A map marker is optional and should follow the same identity and position.

Use a lightweight, readable person label distinct from building labels. The label must be keyboard reachable and activate the same card as clicking the model; mouse hover and focus should give equivalent visual feedback. Pause movement while the label or model is being inspected so a moving target remains usable. The card should identify its subject, link descriptive text to the source without printing a long URL, support Escape/close and return focus. A proximity line is an explicitly scripted scene element; avoid visual obstruction and repeated announcements. Hide or occlude labels when off-screen, distant, behind surfaces, or in another scene.

The template currently includes only `fixed-npc-path.js`, a standalone fixed-point or ping-pong movement primitive with endpoint pauses and input validation. It is not yet integrated with a generic scene renderer, indoor app, card, map or person assets. A downstream prototype demonstrates those pieces and requires further scene-specific and performance checks before any general claim. Keep named-person data, likeness and user-requested lines downstream.

Validation should cover both route directions, endpoint dwell and overshoot, fixed mode, terrain/collision sampling, animation/position synchronization, label and model pointer interaction, keyboard and touch access, card focus and close, scene transitions, proximity threshold, map updates, rendering budget, and source/license provenance. Confirm actual runtime conditions rather than assuming a photo is current.
